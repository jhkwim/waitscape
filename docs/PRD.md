## 1. 왜 지금

Waitscape의 처음 의도는 **AI 코딩 CLI를 쓰는 데 실제로 도움이 되는 도구**였다. 0.5~0.6대에는 스튜디오의 재미 요소(보상·도감·날씨·목격 일지)가 주로 늘었다. 이번 기획은 무게를 다시 도구 쪽으로 옮긴다.

**방향(포지셔닝)**

> 여러 AI 에이전트가 무엇을 기다리고 어디서 헛도는지 먼저 알려 주는 **로컬 관제탑**. 재미는 보상이 아니라 그 신호를 전하는 몸짓이다.

- 새 재미 요소는 "어떤 도구 신호를 표현하는가"를 통과 기준으로 삼는다.
- 같은 신호를 스튜디오는 몸짓으로, 미니 보기는 칩으로, 눈치·업무 모드는 표로 보여 준다.

### 1.1 어떻게 정했나

역할이 다른 에이전트 5개가 서로의 결과를 보지 않고 아이디어를 냈다. 그 뒤 교차 검증과 수렴을 거쳤다.

| 역할 | 본 것 | 핵심 기여 |
|---|---|---|
| 파워유저 | 세션 3~6개를 병렬로 돌리는 하루의 마찰 지점 | "다음에 누구를 봐 줄까"가 하루 수십 번. 킬러는 관제 인박스 |
| 제품 전략가 | 대체재(훅 알림, ccusage, cmux, Claude Code 데스크톱, Codex 앱, 메뉴바 모니터) | "지금 누가 기다리나"는 이미 레드오션. 빈 곳은 여러 CLI에 걸친 판단 보조와 회고 |
| 엔지니어 | 앱이 받는 신호(훅·트랜스크립트·statusline)를 파일:줄 근거로 정리 | 받지만 버리는 신호: `notification_type`, `is_error`, `model`, SessionStart `source` |
| UX 디자이너 | 정보 → 스튜디오 메타포 매핑, 알림 피로 원칙 | 번호표 전광판, 결재 서류함, 멈춤과 휴식 구분 |
| 회의론자 | 사람들이 앱을 끄는 이유, 흔한 아이디어의 함정 | **질문 알림이 틀릴 수 있다**. 새 기능보다 정확도가 먼저 |

수렴 기준은 빈도, 고통, 데이터 준비도(이미 받는 신호인가), 신뢰 위험, 차별성(단일 CLI 앱이 못 하는 것인가)이다.

## 3. A — 신뢰 기반

### 3.1 해결하는 문제

질문 알림이 틀리면 사용자는 알림을 끄고, 알림을 끄면 앱의 존재 이유가 사라진다. 지금 확인된 원인은 다음과 같다(2026-11-04 `main` 500bae4 기준).

1. **유휴 알림이 질문을 만든다.** Claude Code는 턴이 끝나고 약 1분 뒤 `idle_prompt` 알림("waiting for your input")을 보낸다. 앱은 모든 Notification을 받으면 `status = needs_input`으로 바꾼다(`crates/wr-core/src/providers/claude/hooks.rs`의 `"Notification"` 분기, `server.py`도 같다). 그래서 끝난 세션이 "질문 중"으로 되살아난다.
2. **같은 이벤트를 세 곳이 다르게 해석한다.** 같은 파일의 일지 규칙은 "끝난 뒤 오는 알림은 대기가 아님"이라며 `working`일 때만 대기로 센다(`hooks.rs`·`server.py` 일지). 스튜디오 ⚡ 빠른 답장(#115)도 `prev === "working"`이라는 자기 규칙으로 질문을 판정한다(`web/modes/studio/mode.js`).
3. **알림 종류를 버린다.** 훅 입력에는 `notification_type`이 있는데(`permission_prompt`, `idle_prompt`, `elicitation_dialog`, `agent_needs_input` 등) wr-hook과 `hook.py`는 `message` 80자만 남긴다(`crates/wr-hook/src/main.rs`).
4. **권한 요청이 늦게 잡힌다.** `permission_prompt` 알림은 권한 프롬프트가 약 6초 기다린 뒤에야 온다. 바로 잡으려면 `PermissionRequest` 훅이 필요하다(공식 문서: code.claude.com/docs/en/hooks). 단, `permission_prompt`는 도구 승인만이 아니다(예: 샌드박스 네트워크 요청). "권한 = 도구 승인"으로 가정하지 않는다.
5. **훅 없는 모드의 추정이 질문처럼 보인다.** 트랜스크립트만 볼 때 권한이 필요할 수 있는 도구(Bash·Edit·MultiEdit·Write·NotebookEdit·WebFetch·WebSearch·mcp__*)가 8초 넘게 결과가 없으면 "입력 필요일 수도"로 본다(`tonly.rs` `INPUT_GUESS`). 상태에는 이미 `source`·`confidence` 필드가 있지만(`model.rs`), 추정 상태도 "확인이 필요할 수도" OS 알림을 보낸다(`detect.rs`). 오래 걸리는 빌드·테스트가 질문처럼 보일 수 있다.
6. **훅 로그가 계속 커진다.** `~/.claude/waiting-room/events.jsonl`은 wr-hook이 덧붙이기만 하고 아무도 회전하지 않는다. 읽는 쪽은 최근 5000줄만 보고, 파일이 줄면 처음부터 다시 읽는다. MCP 보고 로그(리더가 1MB에서 회전)와 앱 로그(1MB)는 회전이 있다.

> **해결하는 문제:** 앱이 "질문"이라고 말하면 정말 사람이 필요하다는 것을 믿을 수 있어야 한다.

### 3.2 성공 기준 (done when)

- [x] (A1 #118) `done` 또는 `idle` 상태 세션에 `idle_prompt` 알림이 와도 `needs_input`이 되지 않는다. 상태(Rust·`server.py`), 일지 규칙, 스튜디오 빠른 답장이 **같은 판정**을 쓴다(빠른 답장은 코어가 내려 주는 질문 종류·시작 시각을 읽는다).
- [x] (A1 필드 #118 · A2 화면 #120) 세션 상태에 **질문 종류**가 붙는다: `permission`(권한 승인), `question`(AI가 묻는 질문, elicitation·AskUserQuestion·계획 승인). `idle`(턴이 이미 끝남)은 질문이 아니므로 종류 대신 상태를 바꾸지 않는다 — 필드는 A1(#118)에서, 화면(스튜디오 말풍선, 업무 모드 표)과 OS 알림 문구가 종류별로 다르다.
- [x] (A1) `PermissionRequest` 훅을 관찰 전용으로 받는다. 결정을 반환하지 않고 아무것도 출력하지 않고 0으로 끝난다. PermissionRequest가 기록된 뒤 다음 상태 갱신에서 `permission`(추정, `confidence: guess`)으로 보인다.

- [x] (A1) **서브에이전트**(`agent_id`가 있는) PermissionRequest·권한/질문 알림은 메인 세션 질문으로 올린다(질문한 에이전트가 모두 다시 움직이면 풀리고, 질문 직전 상태로 돌아간다 — 메인이 이미 끝났으면 done). 백그라운드 에이전트(`bg`)와 사람 없는 세션(`claude -p` — 훅 env `CLAUDE_CODE_SESSION_ATTENDED=0`, 2.1.318에서 확인)의 권한 요청은 질문으로 보지 않는다.

### 3.3 포함 / 제외

- **포함**: wr-hook·`hook.py`가 `notification_type`과 `PermissionRequest`를 요약해 기록. Rust·`server.py`·스튜디오 빠른 답장의 질문 판정 통일. 업그레이드 사용자 안내 배너. 질문 종류 필드. 근거 배지. 로그 회전. 픽스처·parity 테스트. 문서(MODES·DEVELOPMENT·ARCHITECTURE의 이벤트 목록, CHANGELOG).
- **제외**: 권한 승인·거절을 앱이 대신하는 것(PermissionRequest에서 결정 반환 금지). 터미널에 키 입력 보내기. 훅 matcher를 앱이 몰래 넓히는 것. 새 외부 통신.

### 3.4 위험과 대응

- **훅 설정 변경**: `PermissionRequest`를 더하면 등록 이벤트가 9개에서 10개가 된다. 사용자 설정을 바꾸는 일이므로 기존 설치 화면의 미리보기·백업·동의 흐름을 그대로 탄다. 기존 설치는 설정 탭에서 "일부만 등록됨 — 다시 켜기"로만 보이고, 앱 시작 때 wr-hook 바이너리는 자동 갱신되지만 settings는 그대로라 업그레이드한 사용자는 새 기능이 꺼진 줄 모른다. 그래서 **한 번만 뜨는 안내 배너**("권한 요청을 바로 알려면 훅 다시 켜기")를 범위에 넣는다. 누르면 기존 미리보기·동의 화면으로 간다.
- **비대화형 세션**: 프롬프트를 띄울 수 없는 세션에서도 PermissionRequest 훅이 돈다. 결정을 반환하지 않으면 Claude Code 기본 동작(거부)이 그대로 유지된다. 동작을 바꾸지 않는다는 것을 테스트로 확인하고, 이런 세션은 "권한 대기"로 표시하지 않는다.
- **훅 지연**: PermissionRequest는 사람 앞의 프롬프트를 막는 자리다. wr-hook은 지금처럼 파일에 한 줄 쓰고 바로 끝나야 한다. p95 소요 시간을 측정해 DEVELOPMENT에 적는다.

## 4. B — 관제 인박스

### 4.1 해결하는 문제

세션을 여러 개 돌리면 질문·멈춤·완료가 여기저기서 생긴다. 사용자는 "다음에 누구를 봐 줄까"를 하루 수십 번 정하고, 매번 터미널을 돌며 맥락을 다시 읽는다. OS 알림은 놓치면 끝이다. 그동안 AI는 논다.

> **해결하는 문제:** 지금 내 손이 필요한 세션을 우선순위대로 한 줄로 보여 주고, 키 하나로 그 세션으로 데려간다.

### 4.2 큐 규칙

항목 종류와 우선순위(위가 먼저):

1. `permission` 권한 승인 대기
2. `question` AI 질문(elicitation)
3. 멈춤 의심(`health = stall`)
4. 확인 안 한 완료(`done` + 아직 안 봄)

- 같은 종류 안에서는 오래 기다린 순서다(완료도 같다. 일의 크기는 봉투 두께로만 보여 준다).
- "확인 안 한 완료"는 **새로 만드는 세션 상태**다. 지금 있는 seen/unseen은 퇴근 일보용 집계뿐이다.
- `idle`(턴이 끝나 입력 대기)은 큐에 넣지 않는다. 확인 안 한 완료로 이미 들어 있다.
- 항목에는 세션 이름(프로젝트), 종류 아이콘, 기다린 시간, 한 줄 맥락이 붙는다. 한 줄 맥락은 권한이면 도구와 명령 앞부분(마스킹), 질문이면 알림 문구, 완료면 마지막 단계다.
- "봄" 처리: 바로 이동했거나, 그 세션이 다시 `working`이 되었거나, 사용자가 건너뛰었을 때.

### 4.3 이미 있는 것 (대체·재사용)

- **스튜디오 "다음" 칩**: 질문 먼저, 그다음 완료(🎉/✅)를 보여 주고 누르면 그 층으로 간다(`mode.js`). 인박스는 이 칩을 **코어 큐 함수로 대체·확장**한다. 새 칩을 따로 만들지 않는다.
- **전역 단축키**: 눈치 모드 단축키 인프라(`nunchi.rs`, 설정 화면의 단축키 항목)를 재사용한다.
- **터미널 이동**: cmux·Orca 이동(`terminal.rs`, `nx.go`)을 재사용한다.
- **멈춤 표시**: 스튜디오 "💤 멈춤 의심" 라벨과 멈춤 OS 알림(`detect.rs`)이 있다. 연출을 "눈 뜬 채 톡톡"으로 바꿀 때 💤 라벨과 알림 문구도 같이 바꾼다.

### 4.4 표현

| 화면 | 표현 |
|---|---|
| 스튜디오 | 사장실 문 옆 **번호표 전광판**(지금 차례 번호가 그 직원 머리 위에도 뜬다. 구현: 문 옆엔 자판기·시계가 있고 질문 말풍선이 사장실 가운데를 덮어 사장님 모니터를 전광판으로 씀, #130). 질문 말풍선 테두리는 기다린 시간에 따라 노랑 → 주황(5분) → 빨강(15분). 확인 안 한 완료는 사장실 책상의 **결재 서류함**에 봉투로 쌓이고 일이 클수록 두껍다. 확인하면 "결재" 도장이 쾅 찍힌다. 멈춘 직원은 졸지 않고 눈을 뜬 채 모니터를 톡톡 두드린다(쉬는 직원과 구분). |

### 4.5 상호작용

- **전역 단축키**(기본값은 구현 때 눈치 모드 단축키와 충돌을 보고 정한다. 설정에서 바꿀 수 있다): 큐 맨 앞 세션으로 이동한다.

## 5. C — 측정 먼저, 그다음 🧪 테스트 배지

> 2026-11-05 다시 판단(0.7.0 게시 뒤). 처음 로드맵의 C는 "헛돌기 감지 + 턴 영수증(수정 파일 수·테스트 여부·`git diff --stat`)"이었다. 만들기 전에 이 컴퓨터의 최근 Claude Code 트랜스크립트 40개(사용자 입력 약 970번, 도구 결과 약 4,000건)로 신호를 재 보고 범위를 줄였다. 명령 원문은 보지 않고 숫자만 셌다.

### 5.2 C1 — 실사용 측정(먼저)

- **문제**: B 전체가 "질문 = 정말 사람이 필요함"(A)에 기대는데, §7의 "가짜 질문 알림" 실사용 측정을 아직 하지 않았다.
- **만드는 것**: 훅 로그만 읽어 숫자를 내는 개발용 측정 도구(`cargo run -p wr-core --example asks`, #136, docs/DEVELOPMENT.md "질문 알림 측정"). 외부 통신 없음, 출력에 명령·프롬프트 원문 없음.
- **기준(구현 때 고침)**: "UserPromptSubmit 없이 풀리면 가짜"는 틀렸다 — 권한 승인·질문 답도 다음 PreToolUse로 풀리고, `Resume`(에이전트 결과 보고)은 사람 입력이 아니다. 그래서 **무엇으로 풀렸나 + 알림 뒤 몇 초 만에 풀렸나**로 나눈다. 가짜 후보 = 끝난 뒤 종류 없는 알림이 질문이 됨(옛 훅의 유휴 알림) · 에이전트 결과 보고로 풀림 · 알림 뒤 3초 안에 풀림. 💤 멈춤은 트랜스크립트 판정이라 훅 로그로 재현되지 않아 뺀다. 일지(daylog)에는 질문 종류·끝난 이유가 없어 훅 로그를 쓴다.
- **완료 기준**: 세션 3개 이상 돌린 하루치로 숫자가 나오고, 가짜 후보가 있으면 이슈로 원인을 남긴다.

### 5.3 C2 — 🧪 테스트 배지

- **문제**: 완료를 볼 때 "테스트는 돌렸나, 통과했나"를 터미널을 거슬러 올라가 확인한다.
- **규칙**: 그 턴(UserPromptSubmit ~ Stop)의 Bash 명령 중 테스트 명령(`cargo test`·`npm/pnpm/yarn test`·`pytest`·`go test`·`jest`·`vitest`·`make test`·`node …test….js` 등)을 찾는다. 마지막 테스트 실행의 `is_error`로 ✓ 통과 / ✗ 실패, 없으면 "안 돌림". 사용자 거절·차단은 실행으로 치지 않는다. 명령 원문은 state에 넣지 않는다(결과 기호만).
- **표시**: 📥 다음에 볼 것의 ✉️ 완료 줄, 스튜디오 결재 서류함 봉투·완료 보고, 💼 업무 모드, 🙈 눈치 표. 동작 줄이기와 무관(기호만).
- **지원 범위**: Claude Code(훅·트랜스크립트만 모두). Codex·Antigravity는 도구 정보가 없어 표시하지 않는다.
- **완료 기준**: 판정 규칙의 단위 테스트(픽스처: 통과·실패·안 돌림·거절·여러 번 실행 중 마지막), state 스키마·`types` 갱신, 화면 검수 🔴·🟡 0.

### 5.4 보류(다시 볼 조건)

- 헛돌기 감지: 측정 일지에 실패 연속 횟수를 남겨 보고, 하루에 여러 번 의미 있게 잡힐 때.
